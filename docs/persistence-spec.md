# SAG Video persistence specification

Status: implemented render and shorts worker contract  
Schema version: 5  
Updated: July 22, 2026

## 1. Purpose and guarantees

SQLite is the first persistence backend for SAG Video. The domain and service
layers depend on repository protocols, not SQLite calls, so a later PostgreSQL
or remote-worker implementation can preserve the same semantics.

The persistence boundary guarantees:

- One canonical project head and immutable, queryable project revisions.
- Stable project, asset, track, timeline-item, receipt, job, and artifact IDs.
- Optimistic revision checks at the command boundary.
- Idempotency by `(project_id, request_id)` for commands and receipts.
- Atomic command writes: revision, event, receipt transitions, and observation
  either commit together or roll back together.
- A durable distinction between dispatch, artifact creation, observation,
  observed success, observed failure, execution failure, cancellation, timeout,
  and interruption.
- Provider/model configuration recorded as data, never encoded into the schema.
- Exact reconstruction of every retained project revision without a serialized
  whole-project blob.

This schema does not claim multi-region, multi-writer, or PostgreSQL equivalence.
The initial worker is local and bounded. Secrets and raw participant/customer
data are outside this database.

## 2. Files and runtime configuration

The default database is `.sag-video/sag-video.db`. Managed media, proxies, and
rendered artifacts are files under their configured roots; SQLite holds opaque
identities, hashes, metadata, and provenance, not media bytes or private source
paths.

Every connection uses:

```sql
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;
PRAGMA journal_mode = WAL; -- file databases only
```

`PRAGMA integrity_check` must return `ok` and `PRAGMA foreign_key_check` must
return no rows after migration and in release verification.

## 3. Versioning and migrations

`PRAGMA user_version`, `schema_migrations`, and
`metadata.persistence_schema_version` record the physical schema version.
`Project.schema_version` is separate: it versions the application/domain shape.

Migration rules:

1. Migrations are ordered, deterministic, forward-only Python/SQL functions.
2. Each migration and its data backfill run inside one SQLite transaction.
3. Startup refuses to continue when foreign-key validation fails.
4. A database backup is required before applying a migration to user data.
5. Migrations must preserve stable IDs, request IDs, receipt state, transition
   order, event order, selection order, and reconstructable revisions.
6. Destructive column/table cleanup occurs only after its data has been read
   back through the new schema in the same migration.
7. Rollback means restoring the pre-migration database backup and matching
   media roots; reverse migrations are not improvised against live data.
8. New code must tolerate an already-applied migration and must not rewrite its
   recorded result.

Implemented migrations:

| Version | Name | Effect |
| --- | --- | --- |
| 1 | `normalized_provider_neutral_core` | Replaces project/event/receipt/selection blobs with normalized rows, reconstructs historical revisions, and creates job/provider/candidate tables. |
| 2 | `storage_metadata_and_legacy_asset_truth` | Adds persistence metadata and marks unmaterialized generated slates as pending rather than observed-valid. |
| 3 | `revisioned_asset_snapshots` | Preserves mutable asset metadata at each exact project revision. |
| 4 | `shorts_workspaces_blobs_and_analysis` | Adds workspace lineage, content-addressed media, staged jobs, cached analysis, and suggestion/job linkage. |
| 5 | `normalized_caption_and_crop_children` | Adds normalized revision children for captions and crop keyframes. |

The v1 legacy importer recognizes `body`, `before_body`, and `after_body`
columns, temporarily renames those tables, reconstructs revisions from legacy
events plus the current head, migrates receipts/observations and selections,
then removes only the temporary legacy tables.

## 4. Data conventions

- IDs are opaque `TEXT` values generated by the application. Callers may refer
  to declared IDs but may not choose storage paths from them.
- Times are UTC ISO-8601 strings. Media positions and durations are integer
  ticks at 120,000 ticks/second.
- Boolean values are `INTEGER` constrained or interpreted as `0/1`.
- Hashes are lowercase SHA-256 hex strings when present.
- Revisions start at 1 and increase by exactly one for canonical mutations.
- State strings are application enums. Unknown states fail validation rather
  than being treated as success.
- JSON is canonicalized with sorted keys. Its use is bounded below; it never
  stores an entire project, revision, receipt, or event snapshot.

Allowed JSON columns contain typed but extensible leaf specifications or
evidence: observation details, command arguments, frozen render/capture specs,
provider capability snapshots, provider requests/responses, cost summaries,
provenance, approvals, and suggestion command lists.

Forbidden JSON includes whole project aggregates, whole timelines, raw media,
credentials, provider API keys, OAuth refresh tokens, confidential prompts,
customer data, or a hidden second canonical state.

## 5. Table specification

### 5.1 Schema control and canonical projects

`schema_migrations(version PK, name, applied_at)` is the append-only migration
ledger. `metadata(key PK, value)` stores non-secret database metadata.

`workspaces` owns the authorization boundary shared by a source project and its
derived variants. `projects` stores one row per project: stable `id`, current `name`,
`current_revision`, application `schema_version`, and creation/update times.
It also records workspace membership and immutable source/suggestion lineage
for derived variants. It is the head pointer, not the project body.

`project_revisions` stores immutable revision headers keyed by
`(project_id, revision)`: parent revision, originating request/actor/command,
revision name, canvas dimensions and frame rate, duration, and creation time.
The project foreign key cascades on project deletion.

### 5.2 Assets

`assets` is the current project-scoped asset catalog keyed by
`(project_id, id)`. It stores media kind, source kind, display metadata, opaque
managed URI, observed hash/size/type/duration/streams, derivative relationships,
intake status, and bounded observation summary. `uri` exists for legacy display
identities; new managed inputs use `managed_uri`.

`project_revision_assets(project_id, revision, asset_id, sort_order)` records
membership and library ordering for a revision.

`asset_versions`, keyed by `(project_id, revision, asset_id)`, snapshots the
asset fields used by that revision. This prevents a later probe/status/name
update from changing historical reconstruction. It references both the revision
and stable asset catalog row.

Media bytes never live in these tables. A resolver maps a project-scoped opaque
URI to an allowlisted managed root and verifies the stored hash as required.
`media_blobs` maps a SHA-256 identity to its owning managed-media location so
different project asset IDs can reuse exact bytes without copying them.

### 5.3 Tracks and timeline items

`tracks(project_id, id, created_at)` owns stable track identity.

`project_revision_tracks`, keyed by `(project_id, revision, track_id)`, stores
the revision-specific kind, name, and ordering.

`timeline_items(project_id, id, kind, asset_id, created_at)` owns stable item
identity and immutable media binding. A future command that changes kind or
asset binding must introduce a versioned binding rather than rewriting history.

`timeline_item_versions`, keyed by `(project_id, revision, item_id)`, stores the
complete edit state for the revision: track, name, timeline position/duration,
source range, color/text, transform, fit, opacity, rotation, gain, and mute.
It joins to stable item identity and revision-specific track membership.

`timeline_caption_words`, `timeline_caption_styles`, and
`timeline_crop_keyframes` are ordered, revisioned children. Word timing,
caption presentation, and camera paths remain queryable without a serialized
timeline aggregate.

### 5.4 Events, selections, receipts, and observations

`events` is an append-only semantic mutation log. Each row binds project,
before/after revisions, unique request ID, actor, declared command, bounded
arguments JSON, and time. It contains revision references, never before/after
project blobs. `(project_id, request_id)` is unique.

`selections(project_id, item_id, ordinal)` persists semantic selection order.
Selection supplies context only and grants no authority.

`receipts` stores receipt identity, project/request/command, current status,
actor, exact project revision, bounded payload JSON, and times. The unique
project/request pair is the idempotency key.

`receipt_transitions(receipt_id, sequence, status, transitioned_at)` preserves
the ordered state history. Updating a receipt rewrites this small child set from
the validated in-memory receipt inside the same transaction.

`observations` stores one structured observation per receipt in the current
contract: observer kind/name, failure domain, independence disclosure, result,
inconclusive flag, time, and bounded extra evidence. Re-observation replaces the
current observation atomically; retaining multiple attempts later requires an
explicit attempt/version column.

`observation_findings`, ordered by `(observation_id, sequence)`, stores finding
code, result, severity, human summary, bounded evidence, and compatibility body.
Null `passed` represents unevaluated/inconclusive—not success.

### 5.5 Persistent jobs and artifacts

`jobs` stores one immutable source revision and frozen job specification plus
kind, lifecycle state, stage/status detail, progress, worker lease identity, result artifact,
bounded error, cancellation request, and times. Phase 3 uses one phone render
worker initially.

`job_attempts`, keyed by `(job_id, attempt)`, records each claim/execution
attempt, worker, state, start/end, and error. Startup changes nonterminal work
owned by a dead worker to `interrupted`; it never guesses success.

`artifacts` records stable project/job/asset links, artifact kind, opaque managed
URI, observed hash/size/type, provenance JSON, and time. The file is finalized
atomically before registration. Deleting a job does not delete its artifact row
automatically; its `job_id` becomes null.

### 5.6 Capture, suggestion, and approval workflow

`capture_sessions` stores project, adapter, state, capability snapshot, frozen
request, explicit consent state, result asset, and times. It stores no Android
permission token or captured bytes.

`suggestions` stores a proposal against an exact source revision: generator
kind, state, typed semantic command list, reason, evidence, and confidence.
Suggestions do not mutate projects until accepted through the command boundary.

`analysis_artifacts` caches immutable transcripts and media features by source
hash, analysis schema, provider/version, and settings hash. These typed bodies
are evidence, not canonical project state.

`approvals` records subject, approval type/state, actor, disclosures, and
decision time. Capture, external sharing, candidate acceptance, and publishing
may use separate approval kinds; one does not imply another.

### 5.7 Provider-neutral creative runs

`providers` registers a configured adapter by generic kind, display name,
adapter version, capability snapshot, enabled state, and times. Provider names
and models are rows/configuration, not columns or tables.

`model_runs` stores project/provider/model, purpose, state, provider operation
ID, capability snapshot at dispatch, frozen request, bounded response and cost
summaries, source hashes, and times. API credentials are resolved at execution
from external configuration and never persisted.

`interaction_threads` records optional provider conversation/thread continuity
without making it canonical project state.

`generation_candidates` binds a provider result to its run, optional thread,
artifact, source revision, provenance, observation summary, acceptance state,
and accepted asset. Generated output remains a candidate until observed and
explicitly accepted; completion by a cloud provider is not project success.

### 5.8 Pairing

`pairings` stores a single-use code, workspace, expiry, and consumed flag.
`tokens` stores the current local proof's scoped bearer token, actor, expiry, and
revocation flag. Production deployment should store only a token hash and use a
dedicated credential store; raw provider credentials are never allowed here.

## 6. Repository protocols

`src/sag_video/repository.py` is the storage-neutral service boundary.

- `ProjectRepository`: create/list/head/exact-revision persistence, selection,
  and semantic event append.
- `ReceiptRepository`: idempotent lookup, create, transition/update, and list.
- `JobRepository`: enqueue, exact lookup, atomic claim, update, cancel request,
  and interrupted-work recovery.
- `ProviderRunRepository`: provider registration and model-run create/read/update.
- `ShortsRepository`: content blobs, immutable analysis cache, and suggestion lifecycle.
- `RepositoryUnitOfWork`: one transaction containing repository operations.

The current `Store` implements these runtime-checkable protocols. Services
may receive the narrow protocol they need; they must not depend on SQLite row
objects, PRAGMAs, table names, or a cloud vendor SDK.

Future repository additions should introduce typed records and behavior before
exposing direct CRUD. Artifacts, captures, suggestions, approvals, threads, and
candidates have normalized tables now, but gain public repository methods only
when the corresponding production service is implemented.

## 7. Required transaction and query contracts

### 7.1 Read project head or exact revision

1. Read `projects.current_revision` when no revision is supplied.
2. Read the matching `project_revisions` header.
3. Join revision assets to `asset_versions` in `sort_order`.
4. Join revision tracks in `sort_order`.
5. For each track, join item versions to stable items ordered by
   `(start_ticks, item_id)`.
6. Validate the reconstructed aggregate through the domain model.

A missing project or revision returns not-found; it never falls back to head.

### 7.2 Apply a semantic command

Inside one `BEGIN IMMEDIATE` unit of work:

1. Look up `(project_id, request_id)`; return its existing receipt on retry.
2. Read and compare the exact current revision to `expected_revision`.
3. Validate authority, command declaration, target IDs, and arguments.
4. Create revision `N+1` rows and advance the head.
5. Append the event linking `N` to `N+1`.
6. Write receipt, transition rows, and bounded readback observation.
7. Commit. Any exception rolls back all six writes.

SQLite serializes competing writers through `BEGIN IMMEDIATE`. PostgreSQL uses
an atomic `UPDATE ... WHERE current_revision = expected` or row lock. A stale
revision is a conflict and is never silently replayed.

### 7.3 Media import

The file workflow spans filesystem and database boundaries:

1. Stream caller-provided bytes to a unique managed staging file while hashing.
2. Probe and bound the file; generate derived proxy/thumbnail in staging.
3. Atomically rename completed files into their managed locations.
4. In one database transaction, append asset rows/revision/event and finalize
   receipt/observation.
5. On DB failure, remove newly finalized unreferenced files or leave them for a
   reconciliation pass; never expose them as canonical assets.

Startup/maintenance reconciliation may delete only verified unreferenced files
inside an explicit managed root and should quarantine before permanent removal.

### 7.4 Receipt transitions and observations

Allowed transitions are enforced by the service vocabulary. Terminal states do
not transition except through an explicit future retry receipt. Observation is
bound to the exact receipt/revision/artifact hash. Missing or inconclusive
evidence resolves to observed failure or an explicit inconclusive state, never
observed success.

### 7.5 Job lifecycle

Enqueue freezes project revision and spec. Claim is atomic: select the oldest
compatible queued job, change it to claimed only if still queued, and insert its
attempt. Progress is monotonic by service rule. Cancellation sets a durable
request flag; the worker acknowledges it with a terminal cancelled state.

On restart, claimed/running/rendering/awaiting-observation jobs belonging to the
dead worker become `interrupted` with an error code. Recovery may create a new
attempt only after policy decides whether retry is safe and idempotent.

### 7.6 Provider runs and candidate acceptance

Create a run with a provider capability snapshot, source hashes, and sanitized
frozen request before external dispatch. Store its external operation ID after
dispatch. Provider completion records a response summary and candidate
artifact; it does not edit the project. Observation and human/agent approval
precede a normal `asset.import_derived` semantic command against the source
revision. A stale source revision requires remapping or rejection.

## 8. Indexes and expected access paths

- Project picker: `idx_projects_updated`.
- Revision reconstruction: composite primary keys plus revision asset/track/item
  indexes.
- Undo/audit: `idx_events_project_revision`.
- Receipt panel/idempotency: receipt unique constraint and
  `idx_receipts_project_created`.
- Worker claim: `idx_jobs_state_created`.
- Provider history/candidate review: model-run and candidate project indexes.

New queries require `EXPLAIN QUERY PLAN` verification against realistic row
counts before adding an index. Indexes are not added for hypothetical filters.

## 9. Retention, deletion, and backup

Project deletion cascades canonical revisions, assets, timeline state, events,
receipts, and most workflow rows. It does not itself erase files; a separate
bounded cleanup reconciles managed URIs after commit. Material deletion must be
explicit and recoverable from backup where practical.

Before a schema upgrade, create a consistent SQLite backup using the backup API
or `.backup`, not by copying only the main file while WAL is active. Back up or
snapshot matching managed media for full restoration. Verify backup integrity
before migration.

Revision pruning is deferred. When introduced, it must preserve revisions
referenced by receipts, jobs, artifacts, suggestions, approvals, model runs, or
published outputs and must produce an auditable retention event.

## 10. PostgreSQL/remote-worker portability

Portable semantics are stable IDs, revision checks, idempotency keys, explicit
transactions, frozen job specs, state machines, hashes, and repository records.
Backend-specific mechanics are deliberately not claimed equivalent:

- Replace SQLite `BEGIN IMMEDIATE` with row locks or compare-and-swap updates.
- Replace worker claim with `FOR UPDATE SKIP LOCKED` where appropriate.
- Map booleans/JSON to native PostgreSQL types while retaining validation.
- Use database-generated timestamps consistently and preserve ISO API output.
- Move managed files to an object store through an artifact/media interface;
  commit object identity/hash, never a presigned URL as canonical identity.
- Use advisory locks or uniqueness constraints for singleton reconciliation.

Passing repository conformance tests is necessary but not sufficient to claim
storage equivalence. Crash, isolation, backup, restore, and worker-failure tests
must be rerun against the actual backend.

## 11. Verification checklist

- Migration from a real legacy blob schema preserves head, historical revision,
  selection, receipt, transition, observation, and event identities.
- Restart reconstructs current and exact historical project state.
- No `body`, `before_body`, or `after_body` aggregate columns remain.
- Unit-of-work rollback removes all nested repository writes.
- Duplicate request IDs do not apply twice.
- Foreign-key and integrity checks pass.
- Job claim is exclusive; interruption never becomes success.
- Provider/model rows survive restart and the schema contains no vendor-specific
  names.
- Secrets and absolute private media paths are absent.
